# Phase 6 local verification

Verified on an Apple M4 (16 GB, macOS arm64). This record concerns
reward-driven training: TRL GRPO whose only rewards are Terse `RLWorldActor`
transitions. The gate is verified on an offline tiny fixture. Two real campaigns on
Qwen2.5-0.5B-Instruct followed. **Neither improved the model**: one from the raw
instruct model got almost no reward signal, and one from the approved SFT checkpoint
was vetoed for held-out regressions. Scores use the custom `forge_numeric_v1` scorer on
partitions of the official GSM8K **train** file; they are not GSM8K benchmark results.

## What was built

- **GRPO worker** (`services/training-core/src/forge_training/grpo.py`). TRL
  `GRPOTrainer` pinned at 0.24.0, the release built against the pinned Transformers
  4.57. It runs in the existing worker lifecycle: frozen baseline, training subprocess,
  fresh-process candidate evaluation, manifest and `verify`.
  - The trainer reads only answer-free tasks: manifests with `record_kind: "task"` and
    strict `{id, question}` records, so a record carrying an answer fails to load.
  - Its reward function sends each completion's final-answer action to the
    orchestrator's world gateway. The value it returns is the world's transition
    reward; there is no local scorer.
  - During training, each update must use rollouts generated by exactly the adapter the
    previous update produced. TRL's advantages must equal those recomputed from the
    world rewards, and TRL's logged reward must equal the world rewards' mean.
  - Adapter snapshots are saved and re-hashed from their files. The checkpoint must be
    the final policy of the lineage.
- **World gateway** (`services/orchestrator/src/worlds.ts`): a loopback endpoint
  with a per-job token.
  - For each completion it sends one data-role `reset` with an answer commitment and one
    worker-role `step`.
  - Worlds, episodes and request IDs derive from job, lease generation, lane and
    rollout. Retries therefore replay receipts, and a new attempt never reuses an
    episode.
  - Four lanes (worlds) are stepped concurrently. Update size and count are bounded.
  - Answers come from the allowed partition, checked against the task file.
- **Journal verification** (`verifyWorldRollouts`): reads each world's own event journal
  and requires exactly one transition per rollout, with the recorded reward, state
  version, state hash and task, and no other transitions.
  - The worker runs it with replay, resending every recorded step with its original
    request ID, before reporting completion.
  - The evaluator re-reads it before recording an evaluation.
  - Governance re-reads it before any decision, vetoing with `REWARD_PROVENANCE`
    otherwise.
- **Starting adapters** (`grpo.init_adapter`): GRPO can continue an existing adapter,
  such as an approved SFT checkpoint, identified by its directory hash.
  - The worker stages the adapter as a run input, refuses one with a different base
    model or LoRA settings, and starts the lineage at its saved weights.
  - The run's baseline, the campaign's frozen baseline and governance's regression
    reference all evaluate that adapter. A candidate must therefore beat where GRPO
    started, not the untrained model.
- **Campaign integration**:
  - The director, recipes, preflight and governance accept a campaign method of `grpo`.
  - The data role writes the answer-free projection of a recipe's selection; the
    reviewer recomputes it byte for byte and pins every GRPO setting.
  - New research profiles: `fixture-grpo` (with `--from-sft`, a miniature SFT-then-GRPO
    campaign), and `qwen-grpo --start-adapter <dir>`.
- **Lower-memory model loading**: weights load directly onto the accelerator, giving
  identical logits with a smaller peak (below).
- **Actor package**:
  - `rewardCommitment` takes the reward secret explicitly.
  - The local launcher can restart a runtime on its previous port.

## Gate

**Labeled failure injection** is marked "FAULT" in `tests/worlds.test.ts`.

| Gate requirement | Observed |
| --- | --- |
| Actor-returned rewards feed a real weight update | 48 rollouts, each exactly one `RLWorldActor` transition (48 in the journals). The optimized advantages were recomputed from those rewards during training and again by `verify`. **Control** (labeled stub gateway returning one constant reward): identical rewards give zero advantages. The weights did not change, and the run was refused with no checkpoint. |
| The next rollout uses those weights | At every generation, the policy hash equals the adapter the previous update produced. Snapshots and the checkpoint re-hash from their files to the recorded chain. |
| Trajectories replay | After the restart below, all 48 recorded steps were resent with their original request IDs. Each returned `replayed: true` with the same reward and state hash, and no journal changed. |
| Concurrency | Four worlds were stepped concurrently. Two simultaneous and one repeated submission of one update applied its 8 transitions once. Conflicting, out-of-order, unauthenticated, foreign-task and wrong-size batches were refused. |
| Interruptions | **FAULT:** two applied steps lost their replies and were resent (both replayed). **FAULT:** the Terse runtime was killed with SIGKILL after the 20th transition and restarted on its port. Training completed with exactly one journal transition per rollout. Trainer side: a dropped connection and two 503s were retried with identical bytes. A missing gateway fails closed. |
| A disconnected reward does not count | **FAULT:** the gateway reported one flipped reward. Because the run is internally consistent, `verify` passed. The journals exposed it (`REWARD_MISMATCH`), and the worker and governance run that check before completion or a decision. |

## Autonomous fixture campaign

`npm run research -- fixture-grpo`:
- **Setup:** the director, Relay, Terse actors and Python ran together, and no human
  selected an experiment. Each experiment had 6 updates of 8 rollouts (2 prompts × 4
  samples), all scored by the worlds.
- **Model:** the fixture is a tiny GPT-2, warm-started to answer "What is i plus 1?"
  with `#### k` for k in {i, i+1, i+2}, so rewards vary within groups. It trains on 4
  tasks and is evaluated on 2 development and 2 regression problems.

| Experiment | Development | Rewarded rollouts | Mean reward, first/last update |
| --- | --- | --- | --- |
| Baseline | 1/2 | — | — |
| `r1-explore-concise` | 0/2 | 33/48 | 0.625 / 0.625 |
| `r1-explore-full` | 0/2 | 27/48 | 0.375 / 0.625 |
| `r2-lower_lr-concise` | 0/2 | 27/48 | 0.625 / 0.25 |

The director diagnosed the baseline as a reasoning failure and explored both task
selections. Both regressed, so it revised the selected recipe by lowering the
learning rate, as its rules require. It stopped with `NO_FURTHER_IMPROVEMENT`.

Governance vetoed both reviewed candidates with `REGRESSION`:
- **`r1-explore-concise`:** it lost one development example the baseline answered.
- **`r1-explore-full`:** it lost that example and also dropped on the held-out suite
  (0/2 against 1/2).

In both evidence bundles, the reviewer's own re-read of the journals found 48
transitions for 48 rollouts. Promotion by the director and by the coordinator both
failed with `GOVERNANCE_VETO`. Three reservations were settled at the reserved bound,
and reconciliation finished clean.

On 4 training prompts, a 1-layer model overfits and loses held-out answers. The point
of this campaign is that every reward is the world's and the safeguards catch the
regression, not the scores. Artifacts are under the ignored
`services/orchestrator/artifacts/research-fixture-grpo-1793242326204/`.

## Real campaigns: Qwen2.5-0.5B-Instruct

Both campaigns used the same model revision, seed-42 partitions, development set and
regression suite as Phase 5: 128 training tasks, 16 development and 16 regression
problems. Each update used 8 rollouts (2 problems × 4 samples), and no human selected
an experiment.

**From the raw instruct model (stopped deliberately).**
- **Outcome:** the first experiment ran 16 updates. Only 3 of 128 rollouts earned a world
  reward, and development went from 0/16 to 1/16.
- **No learning trend:** completions ending with a valid `#### N` line stayed at 6 of 64
  in both halves of the run, and completion length and truncation showed no trend.
- **Why it can't learn:** a 4-sample group whose samples all score 0 has zero advantage
  and changes nothing, so almost every update was empty.
- **Predicted beforehand:** a sample of 32 instruct completions had already shown 1
  reward in 32.
- **Stopped:** the campaign was halted during the second experiment.

**From the Phase 5 approved SFT checkpoint.** This is GRPO continuing adapter
`eddf05fc…` (the promoted 64-step SFT recipe). That adapter is the starting policy, so
every comparison below is against it. Re-measured under the current protocol, it
scores 6/16 on development (7 wrong answers, 3 format failures) and 6/16 on the
regression suite. Batch-8 evaluation matched batch size 1 on all 16 examples.

| Experiment | Updates | Rewarded rollouts | Development | Regression suite | Governance |
| --- | --- | --- | --- | --- | --- |
| Starting policy (SFT) | — | — | 6/16 | 6/16 | — |
| `r1-explore-full` | 16 | 17/128 | 6/16 (1 gained, 1 lost) | 5/16 | Vetoed, `REGRESSION` |
| `r1-explore-concise` | 16 | 31/128 | 7/16 (1 gained, 0 lost) | 4/16 | Vetoed, `REGRESSION` |
| `r2-extend-concise` | 32 | 59/256 | 6/16 | not reviewed | — |

The director diagnosed reasoning failures and explored both task selections. It
selected the concise recipe (7/16), extended it to 32 updates, and stopped with
`NO_FURTHER_IMPROVEMENT` when that fell back to 6/16.

Governance then reviewed both explored candidates:
- **Passed:** artifact identity, data and protocol checks; and world provenance, with
  128 rollouts and 128 journal transitions for each candidate.
- **Failed:** both lost held-out regression problems the starting policy answered, so
  both were vetoed. Nothing was promoted.
- **Bookkeeping:** both promotion paths honored the vetoes, all 512 rewards matched
  transitions in 12 world journals, and reconciliation finished clean.

**Interpretation:**
- **Denser signal:** starting from SFT made rewards about 8 times as frequent as from
  the raw model (13–24% of rollouts against 2%).
- **No learning on the training problems:** the reward rate did not rise during
  training (22% to 27%, 16% to 11%, and 24% to 22% between the halves of each run).
- **The one development gain did not generalize:** it was a single example and did not
  hold on held-out problems.

With 128–256 rollouts per experiment and a conservative learning rate, GRPO did not
measurably improve the SFT policy. Governance kept two candidates that generalized
worse from being promoted, which is the required behavior. Larger budgets (more
problems per update, more samples per problem, more updates) are untested here.
Artifacts are under the ignored `services/orchestrator/artifacts/research-qwen-grpo-1793247290/`.

## Memory

Every Qwen run was watched by a script that sampled free memory, swap, system memory
pressure and the job's footprint every 10 seconds. It would stop every process of the
run on sustained low memory, critical pressure, more than 2.5 GB of swap growth, or an
oversized job.

- **An earlier side script** (not part of the phase) bypassed the model-job lock and
  pushed swap to 13 of 14 GB. It was stopped.
- **First campaign attempt:** the guard stopped it 30 seconds in, while Qwen loaded.
  The loader built the float32 model on the CPU and then copied it to the GPU, briefly
  holding it twice. Loading directly onto the accelerator gives identical logits with a
  peak of about 1.9 GB instead of 3.5 GB, and the training core now does that.
- **GPU cache cap:** PyTorch's MPS allocator keeps freed buffers, and the attention
  cache grows by one token per decoding step, so cached memory climbs to whatever cap is
  set.
  - At a cap of 0.6 the baseline evaluation reached a 9.8 GB footprint, and the run was
    stopped by hand.
  - At 0.3 (3.55 GiB) batch-8 generation failed cleanly with an out-of-memory error
    instead of swapping.
  - The campaigns used **0.45** (about 5.3 GB of GPU memory).
- **During training**, the job's footprint held at 8.7–9.9 GB: about 5.2 GB of GPU
  memory plus about 2.6 GB of CPU allocations. System free memory stayed between 20%
  and 40%, pressure was normal or at warning (never critical), and swap grew by at most
  1.6 GB, then shrank. The final campaign finished without a guard trip.
- **Cache release and gradient checkpointing:** the trainer releases cached accelerator
  memory after generation and after each update; the Qwen profile also uses gradient
  checkpointing and one completion per loss micro-batch.

## Interpretation and limits

- **No real-model improvement.** Both Qwen campaigns found none, and governance vetoed
  the SFT-started candidates for held-out regressions. Development and regression sets
  are 16 problems each, so single-example changes are within noise.
- **One process holds every role, as in the earlier local harnesses.** The gateway
  holds the data role's key, the reward secret and the worker key. A deployment needs
  a separate trusted task service and worker identity.
- **Episodes are single-step answer submissions.** The worlds' calculator actions are
  unused, and rewards are binary exact-answer scores with no format shaping.
- **The trainer depends on TRL internals.** It overrides a protected method of the
  pinned TRL version to read the advantages it optimizes. The worker refuses other
  TRL versions; an upgrade needs re-verification.
- **Resumable GRPO is not implemented.**
  - A killed trainer leaves a preserved partial run that is refused
    (`PARTIAL_RUN_DIRECTORY`).
  - The interruption tests cover the reward path (actor runtime, lost replies, gateway
    transport), not optimizer resume.
- **"Replay" means the recorded world transitions.**
  - Re-sending a recorded action returns the same transition from the actor's receipts.
  - Regenerating identical completions is not claimed across devices or kernels.
- **The fixture's development and regression sets are 2 problems each.** Its scores
  carry no benchmark meaning, and all scores use the custom `forge_numeric_v1` scorer.
